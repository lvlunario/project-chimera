## 5–14 minutes — Concept: durable state controls recovery

Consider a link test that may command equipment before recording its result. After a
process interruption, Chimera uses the last durable marker rather than guessing from an
error message or elapsed time.

| Durable task state | What Chimera can prove | Recovery action |
|---|---|---|
| `pending` | The running marker was never committed; the callback was not entered | May execute during explicit resume |
| `running` | The callback started; its external effect/result may or may not exist | Refuse retry and require attention |
| `succeeded` / `failed` / `blocked` | The exact terminal record is durable | Preserve it; never rerun that task |
| `commit_conflict` | Durable content differs from the exact result Chimera intended | Refuse resume/export; investigate |
| completed run | Every task and the final run state validate against the exact plan | May export portable evidence |

An error returned near `COMMIT` is ambiguous: the database may have accepted the write
before the connection failed. Chimera reopens the database under the same lifetime owner
and compares the complete intended record—state, value and error. It continues only on
an exact match. A status word alone is not enough because a wrong value labeled
`succeeded` would contaminate the engineering evidence.

The two records serve different jobs:

- The **journal** supports execution and interruption analysis, including operation IDs
  and incomplete states.
- **RunEvidence** is a strict, portable snapshot of a completed run for storage,
  requirement assessment and handoff.

Conversion requires the exact canonical plan and a completed lifecycle. It invokes no
callbacks. Schema-v1 evidence does not retain the journal operation IDs or plan digest,
so agreement is proved during conversion but that provenance is not carried afterward.
Changing that boundary requires a new versioned evidence contract, not a silent field edit.

## 14–19 minutes — Practical exercise

Before running either demo, classify these interruption points:

1. The process dies before the task receives its durable `running` marker.
2. The process dies after `running`, before a terminal result is durable.
3. SQLite reports an error after the terminal COMMIT, and the reopened full record exactly
   matches the intended value.
4. The reopened row says `succeeded`, but its value differs from the intended value.

Predict whether Chimera should resume, preserve, reconcile or refuse. Expected answers:

1. Resume the still-pending task.
2. Refuse all automatic retry and mark attention required.
3. Accept the exact committed record without repeating the callback.
4. Persist a conflict and refuse resume/export.

Then run the two commands above. For an optional deeper demonstration, run
`python -m examples.commit_recovery_demo`; expected callback counts remain one despite a
synthetic post-COMMIT connection error.
